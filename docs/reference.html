neo4p — internal reference

Validating a planning graph before it reaches a client

How a Neo4j recommendation graph gets snapshotted, checked, and signed off before it's allowed to suggest a financial-planning task to a real customer.

Pipeline
snapshot.py → validate.py
Path cap
MAX_PATHS = 5,000
Audience
engineering + compliance review

Why this exists

The graph is a directed sequence of tasks — emergency_fund → pay_down_high_interest → employer_match_401k → … — connected by HAS_CHILD edges. Where a task's next step depends on the client, one or more CRITERIA_BRANCH edges — each carrying a condition_key/condition_value — fan out from that task to a CriteriaNode per branch ("does the client have an emergency fund on hand?"), and each criteria node's own HAS_CHILD edge points at the task that branch resolves to. Walking the graph from an entry point for a given client produces the ordered task list they're shown.

Because that output reaches real customers, a bad edge, a missing precondition, or an accidental new route through the graph is a compliance and trust problem, not just a bug. validate.py exists to catch that before a graph change ships, not after a client has acted on it.

Why a graph, and not just a rules engine like Drools

A fair challenge, and a common one: the decisions here — is a task complete, is the 401(k) match maxed, does a profile satisfy some condition — are genuinely rules. A CRITERIA_BRANCH edge's condition_key/condition_value, evaluated at a criteria node, is the same shape as a Drools production rule: a condition against client facts, deciding what happens next. Not in dispute.

As a Drools-style rule 
when
    Client(employerMatchPct < capPct)
then
    recommend(increase_401k_contribution);
As a graph criteria node 
employer_match_401k -CRITERIA_BRANCH-> (CriteriaNode)
  condition_key: employer_match_status
  condition_value: not_maxed
(CriteriaNode) -HAS_CHILD-> increase_401k_contribution

Same evaluation, same logic. The difference shows up one level up — in what these decisions compose into.

What a rules engine doesn't give you: not "is this criterion true for this client," but "what is the complete set of task sequences any client could ever be walked through?" That's a reachability question, not a rule-firing one — and a rule engine can't answer it by inspecting its own rule base. The only way is to simulate every fact combination and see what fires, which proves nothing beyond the cases you tried.

employer_match_401k
→ roth_ira → estate_review
→ roth_ira → taxable_brokerage
→ taxable_brokerage

One node, three live traversals in approved_paths today — which one a client takes depends only on which edge condition their facts satisfy at each fork.

That's the value of the graph: enumerate_paths turns "every traversal this can produce" into a millisecond walk, not a testing exercise. The full set is enumerable, diffable across graph versions, and checkable against invariants (check_rules) — because the sequence is data, not a byproduct of firing order.

Rules versus graph is the wrong frame — they compose. A criterion can be evaluated anywhere, Drools included, and handed to the graph as a fact. The graph doesn't replace that logic; it answers what the composition of every correct decision can produce, and proves that set matches what was approved.

Setup & usage

uv sync, then, without Neo4j, using a generated sample graph:

cd src
uv run python make_sample_graph.py
uv run python validate.py snapshots/sample/graph.graphml expectations.yaml

Against a real Neo4j instance:

cd src
NEO4J_URI=bolt://localhost:7687 NEO4J_USER=neo4j NEO4J_PASSWORD=... uv run python snapshot.py
uv run python validate.py snapshots/<timestamp>/graph.graphml expectations.yaml

validate.py writes paths.json and validation.json into the snapshot directory and exits 1 on failure — safe to run in CI.

expectations.yaml

The file every validation run checks the graph against. Kept in version control next to the code, so a graph change that breaks an expected recommendation fails the build instead of reaching a client.

expected_entries / expected_terminals
The only steps allowed to have no predecessor / no successor. A new one showing up means a route changed without anyone intending it to.
approved_paths
Every client journey the graph is allowed to produce. Regenerated from paths.json when a change is intentional — the diff on this list is the record of which journeys a given change added or removed.
scenarios
Concrete client profiles with the step sequence they must produce, for spot-checking behavior the other checks can't see.

The validators

validate.py runs four independent layers. Each catches a different class of problem; none of them subsumes the others.

1

Structural

check_structure()

Is the graph shaped the way you think it is?

  • acyclic — a recommendation flow can never loop
  • entry points match expected_entries — nothing silently added or removed
  • every node reachable from an entry point — no orphaned step
  • every dead end is a declared terminal, not an accident
  • every task node carries rationale + source_doc
  • every CRITERIA_BRANCH edge carries condition_key + condition_value

Cheap, exhaustive. Says nothing about whether the graph's behavior is correct — only its shape and metadata.

2

Path enumeration

enumerate_paths() / check_paths()

Every simple entry-to-terminal route the graph can currently produce, diffed against approved_paths. Flags any journey nobody approved, and any approved journey that's no longer possible.

Exhaustive and exact — when it passes, "every journey this graph can produce" and "every journey someone signed off on" are provably the same set. Also the layer that doesn't scale: past MAX_PATHS (5,000), it refuses to enumerate rather than hang or silently truncate.

3

Rules

check_rules()

Every route checked against approved invariants — precedence and mutual-exclusion — instead of an exact path list.

Covers journeys that don't exist yet, not just the ones enumerated today. Candidates are bootstrapped from the current path list by mine_rules.py and reviewed before they're added to expectations.yaml's rules: list — see Signing off, below.

4

Scenario

check_scenarios()

Does a handful of named, concrete client profiles produce the expected step sequence?

Not exhaustive. Exists because a graph can pass layers 1–3 — correctly shaped, only approved paths, no invariant broken — and still route an actual real-world profile down the wrong one of those approved paths.

Signing off on a graph with combinatorial paths

For whoever is asked to approve a graph or a graph change — typically a compliance or risk reviewer outside the engineering team.

The instinctive request — "review every possible client journey" — is not something a person can do past a few dozen paths, and it gets worse fast: every additional sequential fork roughly doubles the journey count.

At real graph sizes — hundreds of nodes, hundreds of edges — the honest number of distinct journeys is easily in the thousands. MAX_PATHS exists so nobody is ever asked, even accidentally, to review past that point by hand: the script fails loudly instead of quietly succeeding on an unreviewable graph.

Which means "read every path and sign off on each one" cannot be the review process — asking for it produces the opposite of oversight, because nobody actually reads 5,000 sequences, and the sign-off becomes a formality instead of a real check. The review has to be scoped down to something a person can hold in their head and genuinely mean their approval of. Three tiers do that:

  1. 1

    You approve rules, not paths.

    The thing worth a reviewer's judgment is not "is journey #4,812 acceptable" but the invariant behind it — a client must never be told to increase investing before their emergency fund is confirmed funded; debt payoff and credit-limit-increase suggestions must never appear on the same journey; any journey touching a tax-advantaged withdrawal must be preceded by a tax-bracket check. Ordinary suitability-style statements, the kind of judgment a compliance reviewer already makes — and there are a few hundred of them for this graph, not a few thousand paths.

  2. 2

    The rules are enforced automatically, every time.

    Once a rule is written down, it gets checked against every graph change in CI, forever, the same way check_structure and check_paths already run — without depending on anyone's attention on any given day. This is what makes the process reliable, not just honest at the moment of signing.

  3. 3

    You only see raw paths when something is new and high-risk.

    paths.json and approved_paths give an exact diff on every change: which journeys are newly possible, which previously-approved ones vanished. Filtered to journeys touching a flagged high-risk step — money movement, tax elections, debt restructuring — that diff is realistically a handful of sequences per change: small enough to actually read, not skim.

How a rule gets written

Rules aren't invented from nothing — they're read directly off the paths that are already approved:

  1. Start from approved_paths. Look at the journeys already signed off on and ask what invariant explains why those exist and no others do.
  2. State it in plain language. A sentence a compliance reviewer would recognize as an ordinary suitability rule, not a graph-theory statement.
  3. Write it as one of the two shapes check_rules() understands — precedence (a always before b) or mutual_exclusion (a and b never together) — the same small vocabulary mine_rules.py mines automatically.
  4. The reviewer approves the sentence and the rule together — not by re-deriving it, but by confirming the rule actually says what the sentence claims.
  5. It runs in CI on every future change, so it covers paths that don't exist yet, not just the ones that existed on the day of review.

That last step is the actual reason rules beat paths, not just a convenience. A path-by-path review only certifies the paths that exist on the day of the review — the next fork added six months later produces journeys nobody in that review ever saw. A rule, once approved, automatically governs every path the graph will ever produce, including ones that don't exist yet, because it's checked at build time forever, not read once.

mine_rules.py automates step one. Point it at a verified graph's paths.json and it mines every precedence and mutual-exclusion invariant that already holds — a drafted rule set to review, instead of a blank page:

uv run python mine_rules.py snapshots/sample/paths.json
# wrote 9 candidate rules to snapshots/sample/mined_rules.yaml

Review mined_rules.yaml, keep the ones actually meant to hold, and paste them into expectations.yaml's rules: list. From then on check_rules() enforces them on every run — the third validator layer above.

Two rule types, mined from this graph's paths

Precedence

"No client is shown a Roth IRA or taxable-brokerage suggestion before their 401(k) match is captured."

- type: precedence
  before: employer_match_401k
  after: roth_ira

One of 9 precedence rules mine_rules.py found by comparing every pair of steps across the current approved_paths — this one held in all of them, automatically, with no rule hand-written first.

Mutual exclusion

"Debt payoff and a credit-limit-increase suggestion must never appear on the same journey."

- type: mutual_exclusion
  steps: [pay_down_high_interest, credit_limit_increase]

credit_limit_increase isn't a step in this sample graph yet, so the miner can't find this one — a rule like this still has to be hand-written before the step exists, which is exactly the case a miner alone can't cover.

Neither of these needed a reviewer to look at a single row of paths.json — the first was found automatically; the second still took a person noticing a gap the graph has no data for yet. That's the actual division of labor: mine_rules.py drafts what's already true, a reviewer adds what should be true before it's ever tested by a real path.

What sign-off should mean, concretely:

  • the rule set, as written, is correct and complete for the risk you're accountable for
  • the new or high-risk journeys surfaced in this change's diff are acceptable

A reviewer is not attesting to having read every one of the graph's thousands of possible journeys — nobody can, and a process that implies otherwise isn't oversight, it's a rubber stamp with extra steps.

Every task node in the graph carries rationale and source_doc, enforced by layer 1 — treat that as the audit trail. Any flagged step should trace back to why it exists and which policy document put it there.
